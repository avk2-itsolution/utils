# Loop Engineering

Этот skill отвечает только за процесс работы.

Он не заменяет предметные skills:

```text
django-backend-style
frontend-architecture
sync-core-style
```

Предметный skill определяет архитектуру и стиль кода.
`loop-engineering` определяет, как двигаться итерациями, проверять результат и вовремя остановиться.

## Когда использовать

Используй этот skill для нетривиальных задач:

- реализация новой фичи;
- доработка существующего кода;
- диагностика ошибки;
- bugfix;
- refactor;
- написание или исправление тестов;
- проверка сборки;
- изменение нескольких связанных файлов;
- задачи, где возможны несколько гипотез или попыток.

Для простого ответа, маленькой правки в одном месте или объяснения без изменения кода loop не нужен.

## Базовый цикл

```text
цель → контекст → гипотеза → минимальное действие → проверка → вывод → следующая итерация или остановка
```

Каждая итерация должна уменьшать неопределённость или приближать код к готовому проверяемому результату.

## Перед первой итерацией

Перед изменениями:

1. Кратко сформулируй цель.
2. Определи критерий готовности.
3. Назови самый узкий способ проверки.
4. Дай короткий план.
5. Прочитай только релевантные файлы.

Не начинай с широкого поиска, массового рефакторинга или переписывания файлов.

Хороший старт:

```text
Цель:
Критерий готовности:
Проверка:
План:
```

## Одна итерация

Одна итерация должна отвечать на один конкретный вопрос.

Формат мышления итерации:

```text
Гипотеза:
Действие:
Проверка:
Вывод:
```

Где:

- `Гипотеза` — почему проблема возникает или что нужно изменить.
- `Действие` — минимальная правка, точечный осмотр или проверка.
- `Проверка` — тест, команда, diff, import check, сборка или ручная верификация.
- `Вывод` — гипотеза подтверждена, опровергнута или нужна новая итерация.

Не смешивай несколько независимых гипотез в одной итерации.

## Правила изменения кода

Во время loop:

- делай минимальный безопасный diff;
- не исправляй несвязанные проблемы;
- не превращай bugfix в общий refactor;
- не меняй публичные контракты без причины;
- не добавляй зависимости без явного разрешения;
- не переписывай файл целиком, если достаточно точечной правки;
- перед изменением читай соседний код;
- сохраняй существующий стиль проекта;
- не скрывай неудачные проверки.

Если задача стала шире исходной, остановись и явно опиши расширение.

## Проверки

Выбирай самую узкую проверку, которая подтверждает изменение.

Общий приоритет:

```text
targeted test → framework check → lint/typecheck → build → git diff/manual verification
```

Backend/Django:

```text
targeted test → python manage.py check → python manage.py makemigrations --check --dry-run
```

Frontend:

```text
targeted check → lint → build
```

Git-контроль:

```text
git status --short → git diff --stat → git diff
```

Если в проекте есть свои команды проверки, используй их вместо общих.

Если проверку нельзя запустить, явно укажи:

```text
Проверка не запущена:
Причина:
Что проверено вместо неё:
```

## Если проверка упала

Не добавляй хаотичные правки.

Сначала:

1. Зафиксируй ошибку.
2. Определи, связана ли она с текущей правкой.
3. Пересмотри гипотезу.
4. Сделай следующую минимальную итерацию.

Формат:

```text
Проверка упала:
Причина:
Следующая гипотеза:
Следующее действие:
```

Если ошибка не связана с задачей, не исправляй её без необходимости. Укажи её в рисках.

## Правила остановки

Остановись, если:

- критерий готовности выполнен;
- самая узкая нужная проверка прошла;
- достигнут полезный частичный результат;
- 3 итерации подряд не дали результата;
- дальнейшие изменения стали шире исходной задачи;
- нужен доступ, которого нет;
- нужна бизнес-информация от пользователя;
- требуется миграция;
- требуется удаление данных;
- требуется обновление зависимостей;
- требуется рискованное или разрушительное действие.

Не продолжай loop бесконечно.

## Частичный результат

Если полностью завершить задачу нельзя, всё равно дай полезный результат:

```text
Что удалось выяснить:
Что изменено:
Почему остановился:
Что нужно для продолжения:
```

Не выдавай частичный результат за полностью готовое решение.

## Композиция skills

Для backend/Django/Bitrix24 задач используй:

```text
loop-engineering + django-backend-style
```

Для frontend/Vue/Vuetify задач используй:

```text
loop-engineering + frontend-architecture
```

Для задач синхронизации используй:

```text
loop-engineering + django-backend-style + sync-core-style
```

Если задача затрагивает несколько направлений, используй несколько skills одновременно.

Если предметный skill конфликтует с loop-процессом, сохраняй архитектурные ограничения предметного skill и адаптируй loop.

## Антипаттерны

Не делай так:

- начинать с переписывания файла;
- искать по всему проекту без необходимости;
- менять много файлов до первой проверки;
- исправлять всё, что попалось по пути;
- запускать только широкую сборку, когда есть targeted test;
- игнорировать failed check;
- продолжать после 3 неудачных попыток;
- добавлять fallback-логику вместо понимания причины;
- маскировать проблему `return None`, `pass` или широким `except`;
- делать refactor во время bugfix без причины.

## Финальный отчёт

В конце задач с изменением кода всегда дай короткий отчёт:

```text
Изменено:
Проверено:
Результат:
Риски / не проверено:
Следующий шаг:
```

Если проверка падала, укажи это явно.

Если проверка не запускалась, не пиши, что задача полностью проверена.
