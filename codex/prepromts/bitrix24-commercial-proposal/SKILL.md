# Коммерческие предложения по Bitrix24 и интеграциям

## Назначение

Подготавливай технически обоснованные, понятные заказчику коммерческие предложения по:

- внедрению и доработке Bitrix24;
- миграции данных;
- односторонним и двусторонним интеграциям;
- синхронизации с внешними системами;
- смарт-процессам, бизнес-процессам и роботам;
- кастомным приложениям и встройкам в карточки CRM;
- финансовым, логистическим и другим прикладным модулям.

Главный принцип: сначала понять бизнес-процесс и технические границы, затем формировать результат, архитектуру и оценку.

## Обязательный рабочий процесс

### 1. Собери исходные факты

Изучи все доступные материалы:

- расшифровку встречи;
- переписку;
- ТЗ;
- скриншоты;
- текущие документы;
- API-документацию;
- ранее согласованные оценки и формулировки.

Раздели информацию на четыре группы:

1. Подтвержденные требования заказчика.
2. Технически подтвержденные возможности систем.
3. Рабочие предположения.
4. Открытые вопросы и риски.

Не превращай предположение в обещание.

### 2. Восстанови бизнес-процесс

Кратко опиши:

- как процесс работает сейчас;
- где пользователь переключается между системами;
- какие данные вводятся вручную;
- где возникают задержки, ошибки или непрозрачность;
- какой результат нужен пользователю.

Используй цепочку:

```text
Текущий процесс → проблема → целевой сценарий → измеримый результат
```

Не начинай КП с технической реализации. Сначала объясни, что увидит и сможет сделать пользователь после завершения работ.

### 3. Раздели проект на самостоятельные модули

Для каждого модуля определи его тип:

- разовый перенос данных;
- регулярная односторонняя синхронизация;
- двусторонняя интеграция;
- пользовательский модуль внутри Bitrix24;
- общий инфраструктурный слой.

Не смешивай миграцию, синхронизацию и интерактивные действия в один блок.

Для каждого источника зафиксируй:

```text
Источник данных → способ получения → интеграционное приложение → сущности Bitrix24
```

### 4. Проверь внешние системы

Если возможности внешней системы не подтверждены, изучи официальную документацию.

Для каждого нужного набора данных составь таблицу:

| Данные | Метод/API/таблица | Формат | Ограничения |
|---|---|---|---|

Проверяй отдельно:

- способ размещения: self-hosted или внешний сервис;
- доступ к БД;
- API, SOAP/WSDL, REST, XML, файлы;
- авторизацию;
- тестовый контур;
- платные услуги;
- права учетной записи;
- доступность методов для конкретного клиента;
- направление обмена;
- возможность получать события автоматически.

Используй только подтвержденные методы. Если метод не найден, явно укажи, что требуется обследование или подтверждение вендора.

### 5. Спроектируй целевую модель Bitrix24

Определи:

- что остается стандартной сделкой, контактом или компанией;
- какие нужны смарт-процессы;
- какие объекты являются справочниками;
- какие связи нужны между сущностями;
- какие итоговые поля дублируются в сделке;
- где пользователь открывает полные данные;
- нужны ли роботы, бизнес-процессы и права;
- нужна ли отдельная UI-встройка.

Всегда показывай пользовательский путь:

```text
Пользователь открывает сделку
→ видит связанные элементы
→ переходит в карточку объекта
→ смотрит полные данные или выполняет действие
```

### 6. Выбери правильный уровень реализации

Разделяй функции по слоям.

#### Штатный Bitrix24

Используй для:

- хранения сущностей;
- карточек и связей;
- стадий;
- прав доступа;
- роботов;
- уведомлений;
- согласований;
- задач;
- простых итоговых полей.

#### Backend интеграционного приложения

Используй для:

- внешних API и БД;
- парсинга XML/JSON/SOAP;
- сложных расчетов;
- синхронизации;
- дедупликации;
- сопоставления сущностей;
- журналирования;
- повторных попыток;
- контроля идемпотентности.

#### UI-встройка

Используй, когда штатные карточки заставляют пользователя переходить между несколькими сущностями или не дают целостного рабочего экрана.

Встройка оправдана для:

- единой таблицы план/факт;
- агрегированных показателей;
- финансового экрана;
- быстрого добавления нескольких связанных операций;
- массовых действий;
- выбора вариантов из внешней системы;
- сложного сценария в одной вкладке сделки.

Не добавляй UI-встройку только ради отображения одного-двух полей.

### 7. Вынеси общие работы

Если проект содержит несколько модулей, отдельно выдели общий блок.

В общую часть обычно входят:

- проектирование общей модели данных;
- настройка базовых смарт-процессов и связей;
- единая авторизация приложения в Bitrix24;
- развертывание сервера;
- база данных приложения;
- фоновые задания;
- журналирование;
- мониторинг;
- обработка ошибок;
- единые справочники;
- тестовый контур;
- документация по эксплуатации;
- общее приемочное тестирование.

Не включай эти работы повторно в оценки отдельных модулей.

Проверь, чтобы один и тот же смарт-процесс, сервер или механизм синхронизации не был оценен дважды.

### 8. Сформируй содержание каждого модуля

Используй структуру:

1. Название и оценка.
2. Результат с точки зрения пользователя.
3. Какие данные или действия появятся.
4. Где они будут видны в Bitrix24.
5. Технический способ интеграции.
6. Направление обмена.
7. Что не входит.
8. Условия применимости оценки.
9. Детализация работ, если она нужна.

Первый абзац должен отвечать на вопрос:

> Что конкретно пользователь увидит и сможет сделать после завершения работ?

Не начинай модуль словами «Цель — разработать API» или «Будет написан сервис».

### 9. Подготовь оценку

Сначала оцени работу снизу вверх, затем округли для КП.

Для укрупненной оценки используй шаг 5 часов, если заказчик не запросил более точную разбивку.

Типовая структура:

1. Проектирование.
2. Получение и обработка данных.
3. Запись и настройка сущностей Bitrix24.
4. Пользовательская логика или UI.
5. Автоматизация.
6. Тестирование и запуск.

Правила:

- сумма деталей должна точно совпадать с итогом;
- общие работы не должны дублироваться;
- неизвестность не маскируй дополнительными часами;
- при значительной неизвестности добавь отдельное обследование;
- альтернативные варианты оценивай отдельно;
- объясняй, почему один вариант дороже другого;
- не завышай модуль, если данные уже создаются другими модулями.

### 10. Проверь зависимости модулей

Для каждого модуля укажи, какие данные он использует из других частей проекта.

Пример:

```text
Миграция создает заказы и контейнеры.
Интеграция обновляет их статусы.
Финансовый модуль использует те же сущности и не создает дубли.
```

Проверь:

- единые идентификаторы;
- отсутствие дублей;
- источник истины;
- порядок запуска;
- повторное использование справочников;
- одинаковое понимание сделки, заказа, контейнера и терминала.

### 11. Согласуй текст до оформления Word

Рекомендуемый порядок:

1. Короткий анализ задачи.
2. Черновой текст каждого модуля.
3. Проверка оценок.
4. Общий текст КП.
5. Только после согласования — оформление Word.

Не трать время на сложную верстку, пока содержание и оценки меняются.

### 12. Оформи документ как мини-презентацию

Если пользователь просит Word:

- сделай титульную страницу;
- добавь краткое резюме проекта;
- покажи общую архитектуру;
- вынеси общие работы;
- каждому модулю дай отдельную визуальную секцию;
- выдели оценки и варианты;
- добавь итоговую таблицу;
- отдельно укажи условия и исключения;
- используй современную, сдержанную стилизацию;
- избегай перегруженных страниц;
- проверь разрывы страниц и таблицы;
- отрендери документ и визуально проверь каждую страницу.

## Критические вопросы перед финалом

Ответь на них явно или зафиксируй как допущения:

1. Что является источником истины?
2. Это перенос, синхронизация или двустороннее управление?
3. Как система получает данные?
4. Какие данные подтверждены документацией?
5. Какие сущности создаются в Bitrix24?
6. Как пользователь увидит результат?
7. Где используется штатный Bitrix24, backend и UI?
8. Какие общие работы вынесены отдельно?
9. Какие функции не входят в оценку?
10. Сходятся ли суммы по всем разделам?

## Антиошибки

Не делай следующее:

- не обещай методы API, которых нет в документации;
- не называй внешний сервис self-hosted без подтверждения;
- не смешивай XML-выгрузку и API как один способ;
- не называй технический запрос односторонней синхронизацией без пояснения направления бизнес-данных;
- не создавай отдельные смарты для каждого мелкого типа данных;
- не дублируй общие работы в каждом модуле;
- не оценивай повторно данные, уже загруженные другим модулем;
- не добавляй встройку без понятной пользовательской пользы;
- не описывай только технический состав работ — показывай результат;
- не скрывай неопределенность формулировкой «если доступно» без объяснения зависимости;
- не создавай Word до стабилизации текста;
- не включай бухгалтерский учет в Bitrix24, если речь идет только об операционном планировании.

## Definition of Done

КП готово, когда:

- бизнес-задача сформулирована простыми словами;
- каждый модуль дает понятный пользовательский результат;
- техническая реализация подтверждена или помечена как предположение;
- сущности и связи Bitrix24 не противоречат друг другу;
- общие работы вынесены отдельно;
- оценки не дублируются и арифметически сходятся;
- направление обмена указано;
- зависимости и исключения перечислены;
- документ можно показать заказчику без дополнительных устных пояснений;
- Word-документ визуально проверен после рендера.
